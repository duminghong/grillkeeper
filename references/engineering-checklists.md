# 工程场景检查清单（导航索引）

> **本文件是快速索引，不是权威源。**
> 权威内容在 vendor 层，共 64 个专家文件：
> - 路由消歧规则（60+ 条 exact-slug）：`vendor/staff-engineer-mode/skills/staff-engineer-mode/references/routing-matrix.md`
> - 专家检查清单全文：`vendor/staff-engineer-mode/specialists/<slug>.md`
> - 结构化产出模板（71 个）：`vendor/staff-engineer-mode/skills/_shared/assets/templates/`
>
> **路由决策必须读 `routing-matrix.md`**——它对近义场景有精确区分（例：周期任务漏跑/重复触发 → `scheduled-job-reliability`，而数据集新鲜度/回填 → `data-pipeline-reliability`）。下面的 12 张清单只是常见场景的入门摘要，命中后仍应打开对应 specialist 文件。
>
> 原则：**一次任务只走一张主清单**，最多加一张辅助清单。套三张以上说明场景识别失败，回到第一步重新识别。

## 场景识别（四维度）

选清单前先识别：
- **Artifact（产物）**：决策 / 设计 / 计划 / 就绪检查 / 发布 / 排查 / 迁移 / diff 审查
- **Phase（阶段）**：构思 / 设计 / 开发 / 测试 / 合并前 / 发布 / 事故中 / 维护
- **Surface（工程面）**：架构 / 可靠性 / 性能 / 安全 / 数据 / 文档 / 成本
- **Risk（风险）**：可用性 / 正确性 / 隐私 / 兼容性 / 发布安全

工具名/框架名先翻译成能力再识别："用 Redis" → 缓存/派生数据；"用 MQ" → 异步一致性取舍。

## 内置检查清单

> 标题格式：`真实 specialist slug（中文名）`。slug 与 `vendor/staff-engineer-mode/specialists/<slug>.md` 一一对应，命中后直接打开原文。

### architecture-decisions（架构决策）

1. 是否给了两个以上候选方案（含"不做"选项）？
2. 每个方案的四种代价是否量化（开发/运维/认知/迁移）？
3. 决策是否落盘为 ADR？撤销条件是否写明？
4. 依赖方向是否符合分层红线（无反向调用）？
5. 是否引入新单点？单点故障半径多大？

### agent-pr-review（PR/提交审查）

1. 变更是否符合仓库已有编码规范？
2. 是否忠实实现原始 issue/spec（无镀金、无缩水）？
3. 每个发现是否四段式（Symptom → Source → Consequence → Remedy）？
4. 测试是否覆盖变更的行为（不是覆盖行数）？
5. 是否藏有 breaking change（接口/数据/行为）？

### production-readiness-review（发布就绪）

1. 监控告警是否覆盖核心链路（成功率/时长/P99）？
2. 回滚方案是否**验证过**（跑过，不是写过）？
3. 灰度/流量切换策略是否明确（谁、何时、按什么指标切）？
4. 阻塞项/风险项/建议项是否分级列出？
5. 值班响应路径是否明确（谁在几点能几分钟内响应）？

### incident-response-and-postmortems（事故响应）

1. 先止损再定位：回滚/降级/限流优先于找根因
2. 时间线每 5 分钟记一条（事后记忆不可靠）
3. 通讯角色明确：谁知道、谁指挥、谁执行
4. 事后 5-Why + 行动项到人到期日
5. 复盘文档归档到可检索位置

### database-operations（数据库变更）

1. 变更是否向后兼容（先加列→改码→后清理，禁止同步删列）？
2. 大表变更是否有在线 DDL 方案（不锁全表）？
3. 回滚 SQL 是否写好并测过？
4. 备份/恢复是否验证过（恢复演练，不是备份存在）？
5. 慢查询风险是否评估（新索引、执行计划）？

### secure-sdlc-and-threat-modeling（安全审查，逐 sink 输入防御走 input-validation-and-injection-defense）

1. 所有信任边界的输入是否校验（外部回调、用户输入、跨服务）？
2. 注入面是否全覆盖（SQL/命令/模板/路径/反序列化）？
3. 密钥/凭据是否硬编码或进日志？
4. 越权检查是否覆盖横向（他人数据）和纵向（越级操作）？
5. 敏感数据是否进日志/错误信息/前端响应？

### performance-and-capacity（性能容量）

1. 链路 DB 往返数是否量化（N 个 SKU = N×M 次 op × 单次 0.5-2ms）？
2. 重试期望是否算过（= 1/(1-冲突率)）？
3. 资源水位是否超 90%（连接池/内存/IO）？
4. 预算按 P99 算，不按平均值算？
5. 降级路径的容量是否单独核算（降级后流量去哪了）？

### distributed-data-and-consistency（分布式一致性）

1. 强一致 vs 最终一致的取舍是否明示到每个字段？
2. 不一致窗口是否量化（兜底 Job 延迟 + 轮询周期 + 消息延迟）？
3. 幂等键是否真正唯一（DB 唯一索引兜底，不是应用层判断）？
4. 并发覆盖场景是否列出（同一行/键的两个异步写入）？
5. 脏数据检测与修复机制是否存在？

### event-workflows（事件工作流）

1. 消息丢失/重复/乱序各自的处理策略？
2. DLQ 策略 + 人工介入路径？
3. 事件 schema 演化的兼容性（加字段 OK，改字段名禁止）？
4. TraceId 是否跨异步通道串联（回调→outbox→MQ→下游）？
5. 消费者是否幂等（重复消费不产生副作用）？

### observability-and-alerting（可观测性）

1. 黄金指标是否齐（流量/错误/延迟/饱和度）？
2. TraceId 是否全链路串联（含异步段）？
3. 每个告警是否对应一个可执行动作（无动作的告警是噪音）？
4. ERROR 级日志是否有人看（没人看的 ERROR 等于没打）？
5. 仪表盘是否覆盖已识别的破防场景？

### testing-and-quality-gates（测试质量）

1. 测试是否验证行为而非实现（重构实现不炸测试）？
2. mock 是否只用在信任边界（不 mock 自己的领域逻辑）？
3. 覆盖率是否有质量（断言有效性，不是行覆盖数字）？
4. 慢测试是否隔离（不阻塞快速反馈环）？
5. 每个 bugfix 是否伴随回归测试？

### dependency-and-code-hygiene（依赖卫生）

1. 新依赖是否必要（stdlib/平台特性/已有依赖是否已覆盖）？
2. 依赖的维护风险（无人维护/许可证/单点作者）？
3. 升级路径是否明确（锁版本 + 定期升级窗口）？
4. 重复功能的多依赖是否收敛（两个 JSON 库留一个）？
5. 供应链信任（版本锁定/完整性校验）？

## 清单选择规则

- **两个清单都看似匹配**：按 requested artifact 判别，不按共同词汇
- **明确排除**："不改 X"/"不要 Y" 直接从清单里划掉对应条目
- **拿不准**：选最窄的那张清单，跑完后问用户补信息
- **超出工程范围**（营销/合规/人事）：拒绝套用，说明理由

## 红旗（停止并返工）

- 一次任务套用了超过两张清单
- 按关键词匹配选清单，没识别 artifact 和 phase
- 工具名直接出现在审查结论里，未做能力翻译
- 对无发布事件的宽泛请求套用 production-readiness
